## The Challenge

At RapidBoard, we needed a platform that could serve multiple organizations while keeping each tenant's data completely isolated. Additionally, each organization had different roles -- admin, manager, developer, viewer -- each with distinct permissions.

## Architecture Decisions

We chose **Go** for the backend due to its excellent concurrency model and performance characteristics. The multi-tenant architecture was built on a **shared database with tenant isolation** pattern:

- Each table carries a `tenant_id` foreign key
- Middleware injects the tenant context from the JWT claims on every request
- Row-level security policies enforce tenant boundaries at the database level

## RBAC Implementation

The RBAC system was designed around three core concepts:

- **Roles**: predefined sets of permissions (Admin, Manager, Developer, Viewer)
- **Permissions**: granular actions like `project:read`, `project:write`, `user:manage`
- **Assignments**: many-to-many relationships between users and roles per tenant

We implemented a middleware chain that validates the JWT, extracts the tenant and user context, loads their role assignments, and checks permissions before allowing access to any protected endpoint.

## Agent Orchestration

One of the most interesting parts was building an agent orchestration library in Go. The library allows AI agents to:

- Execute multi-step workflows
- Render conditional UI components on the frontend
- Interact with the platform's APIs in a controlled sandbox

The conditional rendering system uses a declarative JSON protocol: agents emit component descriptors and the frontend renders them dynamically, enabling agents to show tables, forms, charts, and custom widgets.

## Key Takeaways

- Multi-tenancy must be designed from day one; retrofitting it is painful
- RBAC needs thorough testing -- missing a permission check can be a security vulnerability
- Go's standard library and concurrency primitives made it an excellent choice for backend services
